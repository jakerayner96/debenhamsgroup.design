Spacing

We measure spacing in gaps. 1 gap = 4px, so gap N = N × 4px. It is the same unit as Tailwind's spacing scale (1 = 0.25rem = 4px at a 16px root), so gap N is Tailwind N: gap 4 = 16px = p-4 / gap-4 / m-4. Every spacing value is quoted in both: gap 4 (16px).

In Tailwind assets/ds/tailwind.preset.js

Add the preset to the front end's config — presets:[require('./assets/ds/tailwind.preset.js')] — and load tokens.css. It maps every DS step to its --gap-* token, so p-4 resolves to var(--gap-4) (16px). It extends Tailwind rather than replacing it, so existing classes keep compiling.

Off the DS scale in today's front-end build (from the dev Storybook's compiled CSS): 2.5 (10px) · 3.5 (14px) · 7 (28px) · 9 (36px) · 11 (44px) · 14 (56px). They still work; each should move to the nearest DS step when that component is next touched.

Writing it down: designs, specs, the catalogue and Storybook quote spacing as gap N (Npx). Sizes (a 50px field, a 24px icon) and type (12/15) stay in px — they aren't spacing.

Breakpoints deferred — deliberate

The live estate applies breakpoints inconsistently per component; the new system exists partly to fix that. Designers work at 390 and 1440. Components are specced fluid-first; the named breakpoint set gets locked once the component audit reveals real reflow needs.

Everything draws at 1pt — borders, dividers, line icons. 2pt is reserved for focus rings and selected states. No shadow scale: the system is flat, hierarchy comes from borders and surface tones.

Motion

Conservative by default. Three durations, two curves, and a global collapse to instant under prefers-reduced-motion — built into the token layer, no per-component work.

TokenValueUse
motion-duration-fast100msMicro — button press
motion-duration-base200msDefault — hover, fade, modal open
motion-duration-slow300msLarger transitions — drawer slide
motion-easing-standardcubic-bezier(.2, 0, 0, 1)Default
motion-easing-emphasisedcubic-bezier(.3, 0, .8, .15)Attention-pulling

No shadows

Deliberately flat. If a future component genuinely needs elevation (a floating popover, say), an elevation token gets proposed then — not pre-emptively.

system / foundations · wcag 2.1 aa — the floor, not the ceiling

Accessibility

Every component targets WCAG 2.1 AA. Non-negotiable: anything that doesn't meet the bar doesn't ship, and a component spec without an Accessibility section isn't finished.

RuleBarDetail
contrast · body4.5 : 1Floor is Grey 5 #6B6B6B — Grey 4 and below never carry body text
contrast · large/UI3 : 118pt+ text and UI components
focusalways visible2pt ring in the brand action colour · full keyboard operation
touch targets44 × 44Minimum on mobile — inline body links exempt where natural
motionreduced-motionAll animation collapses to instant · nothing auto-plays without opt-out
meaningnever colour aloneStatus pairs colour with icon and text · icon-only buttons carry aria-label

Exemptions

The Grey 5 floor applies to text only. Borders, dividers, icons and decorative elements may use any grey — Grey 2 is the typical divider, Grey 4 the standard secondary icon.

Using the system

Brand sites install two packages: the tokens and the components. Set one attribute on the root element and every semantic token resolves to that fascia.

npm install @designsystem-debenhamsgroup/react @designsystem-debenhamsgroup/tokens

Wire in the tokens

/* global css */ @import '@designsystem-debenhamsgroup/tokens/css'; /* tailwind.config.js */ presets: [require('@designsystem-debenhamsgroup/tokens/tailwind-preset')]

Set the brand mode

<html data-brand="debenhams"> <!-- or boohoo · boohooman · plt · karenmillen -->

Use a component

import { Button } from '@designsystem-debenhamsgroup/react'; <Button variant="primary" size="md">Save & continue</Button>

The rules that keep it working

RuleWhy
semantic tokens onlycomponents never touch primitivesBrand colours appear only in the token layer — this is what keeps multi-brand working
one mechanismdata-brand attributeNo per-brand CSS files, no component forks
docs page = specthey ship togetherA component without a docs page doesn't exist

Escape hatch

Components are intentionally constrained. If one genuinely doesn't fit, the source is visible on its page — copy and modify, or raise a request to extend the official component.

Dev alignment

The front-end team's Storybook has 79 components across 178 stories, themed for 21 fascias. This is how it overlays with ours — component by component, token by token — and what the shared build should become.

How the devs build React · Tailwind · per-fascia CSS variables

Components are React with Tailwind utility classes. A variant prop selects a class string (Button has 19). Theming is a flat list of ~25–67 CSS variables per fascia — RGB triplets like --color-primary: 123 231 216 — read by utilities such as bg-primary, font-cta and rounded (which resolves --default-rounding: 0 on PLT and Brand Room — exactly our square modes). Greys are fixed utilities on the same Grey 1–6 ramp we use. Fonts per fascia match ours except Karen Millen (dev runs Work Sans for CTA and headings) and Warehouse (Roboto). A fascia toolbar global switches the theme; our Storybook exposes the same global mapped onto data-brand.

The plan: our catalogue is the visual target. Where a dev component matches, the dev build adopts our tokens and states; where it is partial, the Docs note says what to add on which side; where we have no counterpart it is a new component for us to spec; where they have no counterpart it is a new component for them to build from our story.
